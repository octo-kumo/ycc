## The puzzle, in my own words

A young Elf has been playing on a gift-shop computer and typed a batch of
rubbish product IDs into the database. The shop has already checked most of
the ID space, so I am handed a handful of numeric ranges — `first-last`,
comma-separated, all on one long line — and asked to find, inside those
ranges, the IDs that are *invalid*.

An ID is invalid when its decimal digits are a block of digits written out
twice: `55` (5 twice), `6464` (64 twice), `123123` (123 twice). Leading
zeroes do not exist in an ID, so `0101` is not an ID at all — as a number
that is `101`, and `101` is perfectly valid. Part 1 asks for the sum of the
invalid IDs in the ranges. Part 2 widens the rule: any whole number of
repetitions counts, so `123123123` (three times) and `1111111` (seven
times) are invalid too, and part 2's answer is the sum over that larger
set.

Two details in the statement matter and are exercised by the tests: an ID
that appears in **two** ranges must be counted **once** (the wording is
"all of the invalid IDs that appear in the given ranges", i.e. a set), and
the answer for part 1 on the statement's own worked example is published —
**1227775554** — which is the only number in this folder that the code here
did not produce.


`day02.y` is the only file to compile; `ids.y` (the arithmetic) and
`checks.y` (the property check) sit beside it and are pulled in by

> three levels below the repository root (`examples/aoc/day02`).

```sh
./day02                       # both answers for day02.txt   (this is EXPECTED)
./day02 --brute               # both answers by the element-by-element path
./day02 --check               # the property check (see below)
./day02 --time                # add a timing and allocation line
./day02 --input FILE          # another range file
./day02 --input=FILE
./day02 --help
```

**The documented deterministic run** — `EXPECTED` is the exact stdout of

```sh
./day02
```

and `golden/check.txt` is the exact stdout of `./day02 --check`. Both are
regenerated by

```sh
./day02 > EXPECTED
./day02 --check > golden/check.txt
```

Neither depends on the terminal, the clock (no `--time`) or the network.

### Flags and exit codes

| flag | effect |
|---|---|
| `--input FILE`, `--input=FILE` | read another range file |
| `--brute` | answer by walking every ID in every range (the independent method), not by the generator |
| `--check` | run the property check instead of solving; exit 1 if any check fails |
| `--time` | append a `time`/`heap` line (not in `EXPECTED`) |
| `--help`, `-h` | usage, exit 0 |

Exit 0 on success; **2** on every error path (unknown flag, `--input`
without a value, unreadable or empty input, a malformed ID). No path traps:
a trap prints to *stdout* and would quietly corrupt `EXPECTED` instead of
failing, so every rejection is a message plus a non-zero exit.

## What to look at

1. **`ids.solve`** — the whole pipeline in one function: parse → merge →
   both parts. `./day02` and `--check` both call it, which is deliberate
   (see *Sensitivity* below: the first version had each caller assemble the
   pipeline itself and a defect in `day02.y`'s use of `merge()` was
   invisible to the check).
2. **`ids.rot10` / `ids.has_period`** — the rotation identity that turns
   "is this block repeated?" into a modular multiplication, with no string
   anywhere.
3. **`ids.gen`** — the generator: walk (digit length, period) instead of
   integers, keep the blocks that are not themselves repeats, and each
   invalid ID is emitted exactly once.
4. **`ids.ap_walk`** — part 1's closed form. For a half-length `h` the
   "some block twice" IDs are one *contiguous* interval, so each range
   contributes an arithmetic progression summing to `cnt*(first+last)/2`.
5. **`checks.y`'s `CASES` table** — 16 hand-computed rows, including every
   boundary case a ranges problem is made of, with the arithmetic for each
   in this README.
6. **`golden/check.txt`** — the check's real output, 64 checks.
7. **The `part 2 by digit length` table** in `EXPECTED`: the two smallest
   rows (2 and 3 digits) are small enough to verify by hand from the input,
   and `--check` asserts them against hand-read constants.

## How the solver works

### Two facts, and everything else is bookkeeping

**(1) Rotation.** `10^L - 1` is a string of nines, so modulo it multiplying
by ten is a cyclic left rotation of the `L` digits. Hence

> an `L`-digit number `n` has period `p` **iff** `n * 10^p ≡ n (mod 10^L - 1)`

which decides the question for any `n` with a handful of multiplies and no
digit extraction. `has_period(n, l, p)` is that test; `brute` uses it on
every ID in every range.

**(2) Generation.** Every ID is periodic for its *minimal* period `p0`, and
then `n = b * rep` where `b` is the `p0`-digit block and

```
rep = 1 + 10^p0 + 10^(2·p0) + … + 10^((k-1)·p0),   k = L / p0
```

For a fixed `(L, p)` every `p`-digit `b` works, so the candidate set is one
contiguous interval `[10^(p-1)·rep, (10^p - 1)·rep]`: intersect it with each
range, walk the resulting run of blocks, and keep the ones that are
**primitive** — not themselves a repeat of a shorter block. Requiring a
primitive block makes `p` the minimal period, which is unique, so each ID is
emitted exactly once. Without that filter `1111` would be counted twice (as
`11` twice and as `1` four times); `primitive` is what prevents it, and
`--check` has a case (`1001-1111`) that fails the moment the filter goes.

A 10^10-wide range therefore costs the same as a 10-wide one: the generator
examines 718 candidate blocks for this input where the brute force walks
2285389 IDs.

### Part 1 is not "part 2 with k = 2"

This is the one subtlety, and the property check found it in me. "Some
block **twice**" means "has period `L/2`". With `L = p0·k` that holds
exactly when **`k` is even** — because `k` even is what makes `L/2` a whole
number of periods. So:

- `1111`: minimal period 1, so `k = 4`, even → **part 1** (it is `11` twice).
- `121212`: minimal period 2, `k = 3`, odd → part 2 only (six digits do not
  split into two equal halves).

Bucketing the generator's output by `k == 2` puts `1111` in the part-2-only
bucket and drops it from part 1 entirely. My first version did exactly that;
the check disagreed on `1001-1111` (1010+1111 = 2121 vs 1010) and the check
was right. `ids.gen` now buckets by `k % 2`, and that same classification
gives the decomposition invariant *part 2 = part 1 + the odd-`k` IDs*.

### Three methods, and why three

| method | what it is | where |
|---|---|---|
| **A. brute** | walk every ID in every range, rotation test | `ids.brute` |
| **B. generator** | walk (digit length, period), primitive blocks | `ids.gen` |
| **C. progression walk** | part 1's closed form, part 1 only | `ids.ap_walk` |

`./day02` answers with B (and A for part 1's alternative path) in ~40 µs;
`--brute` answers with A in ~174 ms. Part 1 is computed three independent
ways and part 2 two, and `--check` requires all of them to agree on the real
input *and* on every micro-case.

### Merging, and why the union is the right reading

The ranges are merged into disjoint, sorted spans first (hand-written
insertion sort: Y has no `sort` for records — `fs.sort_names` sorts strings
only). Touching spans (`b.hi + 1 == c.lo`) are joined, empty spans (`lo >
hi`) are dropped and counted. This is what makes "the invalid IDs that
appear in the ranges" a set: without it an ID in two ranges is summed
twice. For this input the 32 ranges are already disjoint and non-touching,
so the merge is a no-op here — the micro-cases `11-22,15-25` and
`11-22,22-33` are where it earns its keep, and `--check` injects the
un-merged path as a defect to prove it (see *Sensitivity*).

### Bounds, stated honestly

- `MAXDIG = 17` digits. The rotation test reduces mod `10^L - 1` and
  multiplies by ten, and `rep_of`/the candidate products must stay inside a
  signed long; 17 is the largest length for which all of that does. A
  longer number in the input is rejected with a message, never a trap.
- Sums are plain `long`s. An input whose *answer* exceeds 2^63 is out of
  scope; this one's answers are ~7·10^10.
- Numbers are parsed by a hand-written strict scanner: `"12a"` is an error,
  not a 12. (`"12a".tonum()` returns **12** — the method form returns
  `long?` but the truncation is silent for trailing junk, which is what
  `examples/SUGGESTIONS.md` §4 asks to be fixed.)

## The property check — `./day02 --check`

A golden file proves determinism, not rightness, and an AoC answer is a
single integer that a wrong algorithm reproduces perfectly. Concretely, while
writing the independent re-derivation for this README I first typed part 1
as "the ID has an even number of digits", which is *not* the rule (1020 is
even-length and is not a block twice). That version reports **68797355494
over 679 IDs** and would have sailed through a golden-file gate with a
perfectly reproducible wrong answer. So nothing in `--check` reads a
reference file or compares against the real input's answer. What it does
instead:

### 1. Hand-computed micro-cases (16 rows, all in `checks.y`)

Every expected sum *and count* below was worked out by hand; the arithmetic
is here so a reader can check it without running anything.

| # | input | part 1 | part 2 | why |
|---|---|---|---|---|
| 1 | `11-11` | 11 (1) | 11 (1) | a range of length one |
| 2 | `11-22,23-33` | 66 (3) | 66 (3) | ranges that **touch** |
| 3 | `11-22,15-25` | 33 (2) | 33 (2) | ranges that **overlap** (22 twice) |
| 4 | `11-22,22-33` | 66 (3) | 66 (3) | a **shared endpoint** |
| 5 | `5-4` | 0 (0) | 0 (0) | a single **empty** range |
| 6 | `1010-1010` | 1010 (1) | 1010 (1) | a value **exactly on a boundary** |
| 7 | `123123-123123` | 123123 (1) | 123123 (1) | a 6-digit doubling, `lo == hi` |
| 8 | `111-111` | 0 (0) | 111 (1) | odd length: part 2 only |
| 9 | `1111111-1111111` | 0 (0) | 1111111 (1) | 7 ones, odd length |
| 10 | `999-1001` | 0 (0) | 999 (1) | 999 = 9 three times |
| 11 | `0101-0101` | 0 (0) | 0 (0) | "0101 is not an ID": the number is 101, which is **valid** |
| 12 | `1001-1111` | 2121 (2) | 2121 (2) | 1010 and 1111; 1111 is both `11` twice and `1` four times |
| 13 | `99-999` | 99 (1) | 5094 (10) | a boundary value, then the triples |
| 14 | `48-48` | 0 (0) | 0 (0) | a **valid** ID alone: nothing at all |
| 15 | `1-1000` | 495 (9) | 5490 (18) | fully derived below |
| 16 | `1212-1212,121-1212` | 3333 (3) | 8217 (11) | 1212 is in **both** ranges, once only |

The arithmetic, row by row:

1. `11-11` — one ID, `11`, which is `1` twice. Both parts 11.
2. `11-22,23-33` — union `11..33`. Two-digit doubled IDs inside: 11, 22, 33
   → `11+22+33 = 66`, and each has repeat count 2 so part 2 is the same.
3. `11-22,15-25` — union `11..25`. IDs 11, 22 → 33. `22` is in both ranges
   and is counted **once**: 55 is what you get if you do not merge.
4. `11-22,22-33` — union `11..33` → 66 (not 88: 22 appears in both).
5. `5-4` — `lo > hi`, an empty range: 0 IDs, both parts 0, no trap.
6. `1010-1010` — `10|10`, `k = 2` → part 1 and part 2: 1010.
7. `123123-123123` — `123|123`, `k = 2` → 123123 in both.
8. `111-111` — three digits, so no two equal halves → part 1 = 0; but `111`
   is `1` three times → part 2 = 111.
9. `1111111-1111111` — seven `1`s, `k = 7` (odd) → part 2 only: 1111111.
10. `999-1001` — `999` is `9` three times → part 2. `1000`: halves `10|00`
    no, repeats of `1` no. `1001`: halves `10|01` no. So 0 / 999.
11. `0101-0101` — parsed as the number 101; 3 digits, no repeat → 0 / 0.
12. `1001-1111` — 4-digit `XX` needs `b ∈ [10,99]` and `1010 ≤ 1212`-style
    bounds: `1010` (`10|10`) and `1111` (`11|11`) → `1010+1111 = 2121`.
    A 4-digit ID cannot be three repeats (4 not divisible by 3), so part 2
    is the same. `1111` is `11` twice (k=2) *and* `1` four times (k=4): it
    is counted once.
13. `99-999` — part 1: only even-length IDs qualify, so just `99` (3-digit
    ones have no halves) → 99. Part 2 adds `111+222+…+999 = 111·45 = 4995`
    → `99+4995 = 5094`, 10 IDs.
14. `48-48` — 48 splits `4|8`, not equal, and is not a repeat of anything →
    0 IDs in both parts. This row exists so that a check which passed here
    would be passing on nothing at all.
15. `1-1000` — part 1: the two-digit doubled IDs are `11,22,…,99`, all nine
    inside, `11·(1+2+…+9) = 11·45 = 495`; the shortest 4-digit ID is 1001,
    outside. So 495 over 9 IDs. Part 2 additionally takes the triples
    `111,…,999`: `111·45 = 4995`. So `495+4995 = 5490` over 18 IDs.
16. `1212-1212,121-1212` — union `121..1212`. Part 1: 2-digit IDs are ≤ 99,
    below 121; 4-digit `XX` in range: `1010, 1111, 1212` → 3333 over 3.
    Part 2: plus the 3-digit triples inside the union, `222,…,999`
    (`111 < 121` is excluded) = `111·(2+3+…+9) = 111·44 = 4884`; a 4-digit
    number cannot be three repeats. So `3333+4884 = 8217` over 11 IDs. Note
    `1212` is in both ranges and appears once.

Each row is checked against **five** numbers: part 1 by brute force, by the
progression walk, and by the generator's even-`k` bucket; part 2 by brute
force and by the generator.

### 3. An independent cross-check on the real input

`--check` runs the real input through **all** methods: part 1 by brute
force, the progression walk and the generator; part 2 by brute force and the
generator; plus the fast path `./day02` actually prints. It also:

- counts the file's bytes independently (`commas + 1 = fields`, one dash per
  field, every field non-empty and non-inverted) and requires the *parser*
  to agree — a parser that dropped the last field cannot;
- requires the merged spans to be **disjoint**, and that merging never grows
  the union;
- requires the brute force to have examined exactly `span_total` IDs (so
  the two methods provably walked the same domain), while the generator
  examined **718 candidate blocks** — a different domain, as designed;
- requires the two halves of the union to sum to the whole, for both parts
  and by both methods.

### 4. Invariants the answer must satisfy

- `part 2 = part 1 + (IDs whose repeat count is odd)`, sums **and** counts.
- `part 1 ≤ part 2` in both sum and count (part 1 is a subset).
- The `part 2 by digit length` table sums to the part 2 answer and to its
  count, has more than one non-empty row, and its widest row is 10 digits —
  the digit count of the largest ID in the input (`9696996784`, hand-read).
- Its **2-digit and 3-digit rows are hand-read anchors**: the only
  2-digit invalid IDs anywhere in the input are `11` (in `1-16`) and
  `33,44,55,66,77,88,99` (in `25-110`), giving 8 IDs summing to 473; the
  only 3-digit ones are `222,…,666` (in `171-671`), 5 IDs summing to 2220.
- No ID is counted more often than the union contains IDs
  (693 ≤ 2285389).
- Every emitted ID is inside the union, checked by **membership**, not by
  comparing bounds.

### 5. Guarding against a vacuous pass

- Every observed value is asserted **present and non-zero before it is
  compared**: the union is non-empty, the brute force's `seen` equals it, the
  generator's `got` flag is set, both parts found a non-zero count, and the
  real input is asserted to be inside the brute-force limit so the
  cross-check cannot quietly skip itself.
- Expected counts come from **outside the code under test**: the
  micro-case table is hand-derived, the statement's 1227775554 is published,
  and the 2-/3-digit rows are read off the input file by eye.
- The micro-case table is checked to contain both zero-answer rows and
  non-zero rows (13 / 3), so the three zeros are not all of it.
- A **deliberately wrong expectation** (`1-1000` claiming 496) is required to
  be *rejected*, and the correct one accepted — a check on the checker.
- The table's row count is asserted (16), so a dropped row shows up.

### 6. Sensitivity: the checks are required to be able to fail

A boundary perturbation: `1-1010` versus `1-1009` must differ by exactly
1010 in sum and by exactly 1 ID — asserted for the generator, the
progression walk **and** the brute force. (The first version of this check
widened the union past the largest ID in the *file*, `9696996785`, which is
valid, so nothing moved and the check correctly failed. A perturbation that
moves no ID cannot prove an equality is sensitive.)

Then defects were **injected** into a copy of the folder and `--check` run
against each. Recorded here so the claim is auditable:

| injected defect | `--check` |
|---|---|
| `ap_walk`: block window uses `floor` instead of `ceil` | **6 FAIL**, exit 1 |
| `gen`: the `primitive` filter removed (double counting) | **8 FAIL**, exit 1 |
| `brute`: period allowed to reach `L` (every ID "periodic") | **15 FAIL**, exit 1 |
| `solve`: `merge()` skipped (overlaps double-counted) | **4 FAIL**, exit 1 |
| `parse`: the last field dropped | **16 FAIL**, exit 1 |
| `brute` part 1: half-length off by one | **16 FAIL**, exit 1 |
| `gen`: bucketed by `k == 2` instead of `k` even | **4 FAIL**, exit 1 |
| `ap_walk`: the `p`-digit clamp on `b` removed | **11 FAIL**, exit 1 |
| `rot10`: the initial reduction removed | 0 FAIL — *correct*: `(x·10ᵏ) mod m == ((x mod m)·10ᵏ) mod m`, so it changes no answer (it is there for range, not arithmetic) |
| `gen`: the digit-length reject removed | 0 FAIL — *correct*: a pure optimisation, the block-window clamp already restricts it |

The two rows with no FAIL are the interesting ones: they are the two changes
that genuinely do not alter any answer, so a check that failed on them would
be wrong.

### What `--check` does *not* cover

It verifies the **solver**, not the printing. A defect in the formatting of
the two headline lines would be recorded faithfully in `EXPECTED` and is not
caught by `--check`; the defence there is that both numbers in `EXPECTED`
are the ones `--check` prints in section 3, so the two files can be read
side by side (and the check does print them).

the real input), which is deliberate — records are references, so each push
needs its own.

## Y notes — the workarounds, and where they are filed

Nothing here needed a compiler fix; these are the language facts the code is
written around, and each is visible in the source rather than worked around
silently.

- **No `sort` for records.** `sort_spans` is a hand-written insertion sort
  (`ids.y`). `fs.sort_names` sorts strings and is no help here.
- **No `break`, no `continue`.** Early exit is a terminal assignment with a
  guard flag (`gen`, `parse`), or a `while (cond && !done)`; "continue" is a
  positive condition wrapping the body. Both idioms appear in `ids.y`.
- **`print` takes exactly one argument.** Output lines are built with `+`
  and f-strings. `print` also appends the newline, so no string literal here
  ends in `\n` — writing one doubles every line (a cosmetic trap I hit).
- **A `match` arm must be followed by `,` or `}`** — newline separation is
  not accepted, whatever the arm body is (`expected ',' or '}' after a match
  arm`). `some(x)`/`none` is the option pattern; a bare identifier in a
  pattern position is read as a type name. `checks.y` uses
  `is_some`/`unwrap` for `fs.read_file`.
- **`"12a".tonum()` returns 12.** The string method returns `long?`, but it
  truncates trailing junk silently, so `ids.parse` has its own strict
  scanner that reports the offending byte. Filed as a missing feature:
  `examples/SUGGESTIONS.md` §4, *A checked integer parse*.
- **`print("x" + "abc"[0])` segfaults** and `+=` with a byte is a compile
  error, so no byte ever reaches a `str` here; digit handling is all
  arithmetic on `long`. Filed: `examples/BUGS.md`, *`str + byte` segfaults*.
- **A record or array literal inside a loop body allocates per iteration**
  (filed: `examples/SUGGESTIONS.md` §7). The only record literals in loops
  are the one-per-*range* pushes in `parse`, `merge` and `checks`, hoisted
  out of the hot paths on purpose — 95 KiB of heap for the whole run.
- **`main()`'s return value is not the exit status** (filed:
  `examples/SUGGESTIONS.md` §15), so this program ends with
  `def main() -> long { … }; exit(main())` and every error path returns 2.
- **`for x in a..b` is half-open**, and `for x in <array>` is a parse error
  (filed: `examples/SUGGESTIONS.md` §6), so strings and arrays are walked by
  index.
- **`str +=` as the last statement of a braced block is quadratic**
  (filed: `examples/BUGS.md`, *A `str +=` in a value-used position makes its
  whole loop O(n²) in heap*). No string is accumulated across a loop
  iteration anywhere in this folder; every per-line string is built by `+`
  from at most a dozen pieces.
- **No `>>>` anywhere.** The solver uses no shift operator at all, so the
  logical-shift-on-a-negative trap cannot apply to it.
- **A missing imported module is reported at the import**, not on the next
  line: `error: cannot find module 'nosuchmodule'`. `fs`, `net` and friends
  resolve from the std pack, so this folder needs no `fs.y` beside it.
