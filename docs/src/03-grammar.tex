\section{Syntax}
\label{sec:grammar}

\subsection{Structure and modules}

A \ty{program} is a sequence of \ty{statement}s executed in order.
Source files may be combined with imports; an import splices the
imported file's text in front of the importing file's own code, under a
namespace alias:

\begin{lstlisting}
import util from "./util.y";   // util.f(...) addresses defs of util.y
import fs;                     // a module by name: fs.read_file(...)
\end{lstlisting}

\noindent An \ic{export \{ a, b \}} clause, when present, lists what a
file offers to importers; its list may run over several lines. It is
\emph{by convention} the last statement of a file, but nothing enforces
that: an import splices the imported file's text and drops every
\ic{export} clause, so a clause anywhere in the file has the same
effect. (A file's defs are spliced whole; namespaces are resolved by
rewriting, not by the export list.) Paths resolve relative to the
importing file's directory, and \ic{.} and \ic{..} segments fold, so
one file reached by two spellings --- \ic{"./m/sub/../m.y"} and
\ic{"./m.y"} --- is spliced once. The fold is lexical: a \ic{..} that
would leave the root is kept as written. A missing module is a fatal
error. Without a
path, \ic{import fs;} finds a module by name: \ic{fs.y} next to the
importing file first, then the standard library's \ic{std/fs.y}. An
import takes a line of its own: only the text up to the semicolon names
the module, and anything after it on that line is dropped --- a second
statement written there never runs, so do not put one there.

A module imported by name keeps its own scope. Its top-level \ic{def}s
and \ic{let}s are reached as \ic{fs.read\_file}, never bare, so they
cannot collide with the program's names: a program may define its own
\ic{exists}, or \ic{let cwd = fs.cwd();}. Inside the module its own
names are bare, and they come before the program's. A binding named
like the module hides it where it is in scope: after
\ic{let fs = \{st: 1\};}, \ic{fs.st} is that record's field. Its type
aliases are its own the same way: the program names them \ic{m.T}
(\ic{let p: geo.Pt = geo.origin();}, a pattern \ic{geo.Pt p => ...}) and
may declare a \ic{Pt} of its own, which the module's code never sees.

The files imported by path share one namespace with the program:
\ic{util.f} is rewritten to plain \ic{f}, and the alias only says which
file a name comes from. A \emph{type} alias from such a file is reachable
both ways --- \ic{m.T} and bare \ic{T} are one declaration, checked in every
position a type can appear --- which is the one respect in which the two kinds
of import now behave alike. A module imported \emph{by name} still needs its
prefix on a type, as above.
A later top-level \ic{def} replaces an earlier one of the same name.
Within one file that is deliberate (the last definition wins), and it is
\emph{not} silent: declaring a name twice in one file is a warning that
names the line the earlier declaration is on, because the case that
matters is the one nobody notices --- an edit that left an old copy
behind, shadowing the new one, where every read of the file shows the
copy that is not the one called (\ic{'f' is declared more than once; the
last declaration counts}). Across files it would silently hand one file's
callers another file's function, so a \ic{def} that replaces one from
another file is an error, reported at the later definition and naming the
other (\ic{duplicate definition 'helper': m.y:4 defines it too}). The standard-library code the compiler
splices in itself is the exception: a program's own \ic{readline}
replaces the prelude's. Nested \ic{def}s and top-level \ic{let}s follow
the usual scoping, as if the files were one text.

A file's bytes can be compiled in as a string: on a line of its own,

\begin{lstlisting}
embed HELP from "help.txt";   // const HELP = "<the file's bytes>";
\end{lstlisting}

\noindent declares the \ic{const} with the file's contents, read when the
program is compiled. The path resolves like an import's, a missing file
is a fatal error, and line numbers after the declaration are unchanged.

\subsection{Target overlays}
\label{sec:overlays}

A file \ic{NAME.y} may carry a file for one target beside it:
\ic{NAME.TARGET.y}, where \ic{TARGET} is \ic{linux}, \ic{windows},
\ic{aarch64}, \ic{kernel} or \ic{web}. When the compiler builds for that
target it merges the two, so one module can have a Linux body and a web
body without an \ic{if}:

\begin{lstlisting}
// gui.y
def open(w: long) -> bool { ... };   // the Linux body
// gui.web.y
def open(w: long) -> bool { ... };   // replaces it under --target=web
\end{lstlisting}

\noindent Only the current target's file is read: \ic{gui.windows.y} is
ignored on the web. The merge works on declarations, not text:

\begin{itemize}
\item a \ic{def} or \ic{ndef} the base has replaces it in place. Its header
  must match token for token from \ic{def} to the body's opening brace ---
  parameter \emph{names} may differ, their types, defaults and the return
  type may not. A changed signature is an error naming both files and lines;
\item a \ic{let} or \ic{const} the base has is replaced;
\item a \ic{type} the base has may only be a \emph{superset record}: every
  base field must still be there with the same type text, and the overlay may
  add fields. A union cannot be replaced;
\item an \ic{export} clause is merged as a union: the base's list gains the
  overlay's new names;
\item every other declaration is appended after the base's last line. It must
  not be needed by the base's top-level initialisation --- the base's globals
  are set up before it exists;
\item the overlay holds declarations only (and imports, which are hoisted);
  a statement there is an error. Two declarations sharing a line is an error
  only when one of them is replaced, because the merge works in whole lines.
\end{itemize}

\noindent Each line keeps its own file and line, so a diagnostic points into
the file it came from, and \ic{ycc --emit=source} prints the merged text with
\ic{// file:line} comments. A \ic{NAME.TARGET.y} with no \ic{NAME.y} is the
error \ic{overlay NAME.TARGET.y has no base NAME.y}. Compiling the overlay
itself, as in \ic{ycc --target=linux NAME.linux.y}, builds the merged program.
The standard library's files take overlays too (the web build of \ic{gui} is
\ic{gui.web.y}), and a packed compiler links a unit's variant for the current
target.

\subsection{Packages}

A \emph{project} is a directory with a manifest, \ic{y.toml}, and
\ic{ycc build [DIR]} builds it (\ic{DIR} defaults to the current one):

\begin{lstlisting}
[package]
name = "app"                  # required: an identifier, no keyword
lib = "src/lib.y"             # optional: what importers of app get
src = ["src"]                 # optional: where bare imports also look

[bin]                         # the programs: build/app from
app = "src/main.y"            #   src/main.y, build/tool from
tool = "src/tool.y"           #   src/tool.y

[dependencies]
json = { path = "../json" }
http = { git = "https://example.com/http.git", rev = "v1" }

[defines]                     # build inputs for meta blocks
level = "2"
\end{lstlisting}

\noindent The manifest is a subset of TOML: one \ic{[table]} header or
\ic{key = value} per line, a value being a string (\ic{"..."} with
\ic{\textbackslash\textbackslash}, \ic{\textbackslash"},
\ic{\textbackslash n} and \ic{\textbackslash t} escapes, or
\ic{'...'} as written), an array of strings, or an inline table of
strings; \ic{\#} starts a comment. \ic{[package]} may also carry
\ic{version}, \ic{description}, \ic{license} and \ic{authors}, which
the build ignores; any other key or table is an error. A bin may not be
named \ic{obj} or \ic{git} (\ic{build/obj} keeps the package objects,
\ic{build/git} the clones). Paths are relative to the manifest's
directory.

\ic{[defines]} holds string-valued build inputs; a meta block reads them as
\ic{YCC.defines} and the command line's \ic{-D} and \ic{-U} override them
(Section~\ref{sec:ycc}). They are part of a package's cache key, so changing
one recompiles it.

A dependency is another project, named by its own manifest exactly as
the key names it, that has a \ic{lib}. Its \ic{lib} file and the files
that file imports form a \emph{package}, compiled on its own: in a bin,
or in a package's \ic{lib}, \ic{import json;} (on a line of its own)
makes the top-level \ic{def}s and \ic{let}s of the \ic{json} package
available as \ic{json.parse(s)}, \ic{json.limit}. Such names stay
qualified: a bin's own \ic{parse} is another function. Parameter
defaults and optional parameters work across the boundary; a package's
globals are read-only to its importers (\ic{cannot assign to constant
'json.limit'}), and its type aliases are its own (an importer spells
the type out). A project's own \ic{lib}, when it has one, is a package
its bins import the same way. A bare import names a dependency before
any file: \ic{import json;} in a project depending on \ic{json} is the
package even next to a \ic{json.y}; otherwise it looks next to the
importing file, then in the \ic{src} roots of the importing file's
project, then in the standard library.

The packages of one step --- those that depend only on what is already
compiled --- are compiled in parallel, several at a time; what each one
writes is exactly the object the build would have written, so the
programs a build produces and the packages it recompiles do not depend
on it.

Each bin is linked with the packages it imports, directly or through
other packages, and each package's top-level code runs once, before its
importers' (dependencies first). A package may depend on others; a
dependency cycle is an error, and so is one name coming from two
different places --- unless the project itself declares that name,
which settles it for every package. \ic{y\_} names are global across
packages (they are the runtime's override hooks).

\ic{build/obj} keeps each package's compiled object. A package compiles
again only when its text, the paths it was read from, the compiler, or
the interface of a package it imports (the names, types and defaults it
exports) changed; a change elsewhere in a dependency leaves its
importers' objects as they are. \ic{ycc build -g} links the same
objects with line information. A package's warnings
(Section~\ref{sec:warnings}) print when it compiles, and \ic{--warnings=none} drops
them.

A git dependency is cloned into \ic{build/git} --- its \ic{rev} (a tag,
branch or commit), or the default branch without one --- and pinned in
\ic{y.lock} to the commit it resolved to; later builds use that commit
until its \ic{y.lock} entry is deleted. \ic{ycc vendor [DIR]} copies the
project's git dependencies into \ic{vendor/}, which then wins over the
network. Git runs through \ic{/bin/sh} with the compiler's environment.

\subsection{Declarations}
\label{sec:declarations}

\begin{align*}
\ty{declaration} ::={}& \ic{let}~\ty{name}~[\ic{:}~\ty{type}]~\ic{=}~\ty{expr}~\ic{;} \\
  |~& \ic{const}~\ty{name}~[\ic{:}~\ty{type}]~\ic{=}~\ty{expr}~\ic{;} \\
  |~& \ic{def}~\ty{name}~\ic{(}~\ty{params}~\ic{)}~[\ic{->}~\ty{type}]~\ty{block} \\
  |~& \ic{ndef}~\ty{name}~\ic{(}~\ty{params}~\ic{)}~\ic{->}~\ty{type}~[\ic{=}~\ic{label}]~\ic{;} \\
  |~& \ic{type}~\ty{name}~\ic{=}~\ty{type}~\ic{;}                && \text{(alias)}
\end{align*}

\ty{params} is a comma-separated list of \ty{name}~\ic{:}~\ty{type},
each optionally followed by a literal default (\ic{name: T = literal}).
A parameter with a default may leave its type out: it is the literal's
(\ic{punct = "!"} is a \ic{str}). Every parameter has a type --- one with
neither is an error, \ic{parameter 'x' has no type (annotate it)}.
Return types are optional (inferred from the body,
Section~\ref{sec:annotations}). A \ic{const} name cannot be rebound: \ic{=},
the compound assignments and \ic{++}/\ic{--} on it are rejected
(\ic{cannot assign to constant 'n'}, with the operator in parentheses
for the compound forms). The \emph{value} is constant too: a store that
reaches it through the name is refused as well, so \ic{a[i] = v},
\ic{r.x = v}, \ic{m["k"] = v} and \ic{a[lo:hi] = v} are all errors
(\ic{cannot modify 'a': it is a constant}), while the in-place
\ic{+=}/\ic{*=} on a \ic{const} array is refused as a rebinding of the
name (\ic{cannot assign to constant 'a' ('+=')}) --- a \ic{const} array, record
or map is a value to read, not a shared buffer to hand out and keep
patching. A pointer is the way to hand one out knowingly: \ic{\&a[0]} is a
\ic{*long} and \ic{*p = 1} stores through it, which the checker does not
follow.

A parameter may be \emph{optional}, written \ic{name?: T}: its type
becomes \ty{T?} and a caller may leave the argument out, which is
\ic{none} inside the function (Section~\ref{sec:type-records} for the
same mark on a record field). Three rules keep the list readable, and
each names the mistake:

\begin{center}
\begin{tabular}{@{}>{\raggedright\arraybackslash}p{0.30\linewidth}@{\quad}>{\raggedright\arraybackslash}p{0.60\linewidth}@{}}
\toprule
mistake & message \\
\midrule
no type after it &
  \ic{optional parameter 'x' needs a type ('x?: T')} \\
a default as well &
  \ic{optional parameter 'x' cannot have a default} \\
one after it &
  \ic{required parameter 'y' cannot follow optional parameter 'x'} \\
\bottomrule
\end{tabular}
\end{center}

\noindent The third is the reading order: optional parameters come last.

\begin{lstlisting}
def draw(canvas: Canvas, fg?: Color, bg?: Color) -> void { ... };
draw(cv);                     // fg, bg: none
draw(cv, {r: 255});           // fg: some({r: 255}); bg: none
\end{lstlisting}

Function literals may also appear bound or anonymous:
\ic{let f = def (x: long) -> long \{ x \};}.

\paragraph{\texorpdfstring{$\mathrm{ndef}$}{ndef}.}
The last declaration form has no body: its implementation is an assembly
label, and the declaration is the compiler's promise about what that label
does. \ic{label} is a string naming the symbol; left out, it is
\ic{y\_} plus the declared name. Four rules, each with its own message:

\begin{center}
\begin{tabular}{@{}>{\raggedright\arraybackslash}p{0.30\linewidth}@{\quad}>{\raggedright\arraybackslash}p{0.60\linewidth}@{}}
\toprule
mistake & message \\
\midrule
the label has no \ic{y\_} &
  \ic{ndef label 'x' must start with 'y\_'} \\
no return type after \ic{->} &
  \ic{ndef 'f' needs a return type} \\
inside a function &
  \ic{ndef 'f' must be at the top level} \\
another top-level name already taken &
  \ic{'f' is a ndef and is declared again at the top level} \\
\bottomrule
\end{tabular}
\end{center}

\noindent The return type is required because there is no body to infer it
from. A label with no assembly behind it is found when the code is assembled,
which is as late as it can be found: \ic{error: assemble: undefined label 'y\_f'}.
There is no linker here --- the compiler has its own assembler and ELF writer
--- so the prefix is \ic{assemble}, not \ic{link}.

A \ic{ndef} is called with the ordinary convention (arguments pushed
on the stack, the result in \ic{\%rax}), so it reaches the runtime's
string and array helpers, and any assembly a package contributes. It cannot
reach a helper written for the binary-float convention, which takes its
operands in \ic{\%xmm0} and \ic{\%xmm1} (\ic{math.fmod} in the prelude is
one). Nothing checks the declared types against the label --- the assembly
is opaque, exactly as an \ic{extern} declaration in C is --- so the promise
has to be kept by hand.

\begin{lstlisting}
ndef hash2(a: str, b: str) -> long = "y_str_cmp";  // a promise
ndef heap_used() -> long;                          // means y_heap_used

print(hash2("abc", "abd") < 0);
\end{lstlisting}

\subsection{Types}
\label{sec:type-grammar}

\begin{align*}
\ty{type} ::={}& \ic{long} \mid \ic{int} \mid \ic{byte} \mid \ic{bool}
              \mid \ic{float} \mid \ic{str} \mid \ic{bigint} \mid \ic{void} \\
  |~& \ic{mutex} \mid \ic{sem}                   && \text{(Section~\ref{sec:builtin-threads})}\\
  |~& \ic{[}~\ty{type}~\ic{]}                    && \text{(heap array)}\\
  |~& \ic{[}~\ty{type}~\ic{;}~\ty{nat}~\ic{]}   && \text{(fixed array)}\\
  |~& \ty{type}~\ic{?}                           && \text{(option)}\\
  |~& \ic{*}~\ty{type}                           && \text{(pointer)}\\
  |~& \ic{(}~[\ty{type}~\{,\ty{type}\}]~\ic{)}~\ic{->}~\ty{type}
                                                 && \text{(function)}\\
  |~& \ic{(}~\ty{type}~\ic{,}~\ty{type}~\{,\ty{type}\}~\ic{)}
                                                 && \text{(tuple)}\\
  |~& \ic{\{}~[\ty{field}~\{,~\ty{field}\}]~\ic{\}}
                                                 && \text{(record shape)}\\
  |~& \ic{\{}~\ty{type}~\ic{=>}~\ty{type}~\ic{\}}  && \text{(map)}\\
  |~& \ty{type}~\ic{|}~\ty{type}                 && \text{(union of records)}\\
  |~& \ic{packed}~\ic{\{}~\ldots~\ic{\}}
     \mid \ic{bits}~\ic{u8}~\ic{\{}~\ldots~\ic{\}}
                                                 && \text{(Section~\ref{sec:pointers})}\\
  |~& \ic{i8} \mid \ic{i16} \mid \ic{u16} \mid \ic{i32} \mid \ic{u32}
     \mid \ic{u64}                               && \text{(Section~\ref{sec:pointers})}\\
\ty{field} ::={}& \ty{name}~[\ic{?}]~\ic{:}~\ty{type} && \text{(\ic{?}: optional)}
\end{align*}

\noindent A record type is structural and its field order free
(Section~\ref{sec:type-records}); it lists every field of its records
(\ic{\{ k: str \}} is the record with the one field \ic{k}); a field
written \ic{name?: T} is optional, of type \ic{T?}, and a literal may
leave it out (Section~\ref{sec:type-records}). A union's
members are record types (Section~\ref{sec:type-unions}). \ic{nat} is an integer literal from 0 to $2^{31}-1$ (2147483647),
decimal or radix (\ic{[0; 0x10]}); a float, a larger or negative number
or a name there is an error at the size. The type name
\ic{int} is accepted as a synonym of \ic{long} in annotations, and
\ic{bigint} is the arbitrary-precision integer type
(Section~\ref{sec:type-bigint}). A tuple type \ic{(long, str)} is a
record whose fields are positional (Section~\ref{sec:type-records}). The
sized integers (\ic{i8} \ldots\ \ic{u64} and their \ic{be}/\ic{le}
forms), \ic{packed \{ \ldots \}} and \ic{bits u8 \{ \ldots \}} are the
raw-memory types detailed in Section~\ref{sec:pointers}. Any other
name must be a \ic{type} alias in scope: \ic{let s: strr = "x"} is
rejected as an unknown type.

The last row, \ic{A | B}, is a form of a whole annotation only: a
\ic{let}, a parameter list, a return type or a \ic{type} declaration.
It cannot appear inside another type --- \ic{[Circle | Rect]},
\ic{\{ shape: Circle | Rect \}} and \ic{(Circle | Rect) -> R} are all
rejected at the \ic{|} --- so a union used in a nested position goes
through an alias, as recursive types do:

\begin{lstlisting}
type Shape = Circle | Rect;
let shapes: [Shape] = [];       // the union, named
def area(s: Shape) -> float { ... };
\end{lstlisting}

\subsection{Statements}

\begin{align*}
\ty{statement} ::={}& \ty{declaration} \\
  |~& \ty{expr}~\ic{;} \\
  |~& \ty{assignment}~\ic{;} \\
  |~& \ic{return}~[\ty{expr}]~\ic{;} \\
  |~& \ic{break}~\ic{;} \\
  |~& \ic{continue}~\ic{;} \\
  |~& \ty{block} \\
  |~& \ic{if}~\ic{(}~\ty{expr}~\ic{)}~\ty{block}~[\ic{else}~(\ty{block} \mid \ty{statement})] \\
  |~& \ic{if}~\ic{let}~\ty{pattern}~\ic{=}~\ty{expr}~\ty{block}
        ~[\ic{else}~(\ty{block} \mid \ty{statement})] \\
  |~& \ic{while}~\ic{(}~\ty{expr}~\ic{)}~\ty{block} \\
  |~& \ic{for}~\ic{(}~[\ty{stmt}]~\ic{;}~[\ty{expr}]~\ic{;}~[\ty{stmt}]~\ic{)}~\ty{block} \\
  |~& \ic{for}~\ty{name}~\ic{in}~\ty{expr}~\ic{..}~\ty{expr}~\ty{block} \\
  |~& \ic{foreach}~\ic{(}~\ty{name}~\ic{in}~\ic{expr}~\ic{)}~\ty{block}
       && \text{(array, map, string)}
\end{align*}

\noindent \ty{block} is \ic{\{}~\ty{statement}\(^*\)~[\ty{expr}]~\ic{\}}:
a block is an \emph{expression} whose value is its trailing expression
(if any). A block with no statements is legal and void, and a trailing
\ic{;} makes a block void whatever else is in it. Note that \ic{\{\}}
in an \ic{expr} position is not this at all --- it is the empty record
(Section~\ref{sec:type-records}) --- so a block used as a value
has to hold a statement. A statement-form \ic{if} is an expression too, and a
\ic{[} after it indexes that value --- \ic{if (c) \{ A \} else \{ B \}["k"]}
indexes the chosen arm --- so a \ic{;} after the block is what keeps the two
apart. (An \ic{if} with no \ic{else} is \ic{void}, so it has no value to index.)
(\ic{if let} is included: a \ic{[} on the line after one is an index of the
narrowed \ic{if}, not the next statement, and the fix is the same \ic{;}.
This one shape was read as a checker bug --- "the narrowed field lost its
type" --- eight times before the diagnostic named the \ic{;}.)
Indexing one that has no value (its arms are statements, or disagree) says
so and names the \ic{;} rather than reporting the \ic{[}: \ic{cannot index
this 'if', which has no value: add a ';' after it to make it a statement}. Statements are separated by \ic{;}, which may be
left out only after a statement that ends in \ic{\}} (an \ic{if},
loop, \ic{def} or block) or before the \ic{\}} closing the block:
\ic{f() g()} is an error, and so is any token the grammar does not
expect --- nothing is skipped silently. \ic{foreach} iterates
the elements of an array, the \emph{keys} of a map and the \emph{bytes}
of a string --- so \ic{foreach (c in s) \{ print(c); \}} walks \ty{s}
without copying it; the \ic{for} range form iterates \ic{lo..hi}
with the low bound inclusive and the high bound exclusive. A C-style
\ic{for} without a condition loops until a \ic{return} leaves it, as in
C. A C-style \ic{for} binds its head like a \ic{let}, so the names it
declares are still visible after the loop, holding the value the loop
last gave them. A \ic{for x in a..b} or \ic{foreach (x in a)} variable
belongs to its loop and is gone after it --- reading it there is
\ic{undefined variable 'i'}.

\noindent \ic{break} leaves the innermost enclosing loop and
\ic{continue} starts its next turn: \ic{continue} in a C-style
\ic{for} runs the step first, and in a \ic{foreach} or a
\ic{for x in a..b} it takes the next element. A loop nested inside
another is left alone, so \ic{break} never leaves more than one. Either
word outside a loop is the error \ic{'break' outside of a loop}, and
either inside a \ic{def} nested in a loop is \ic{'break' cannot cross
a function boundary} --- a closure is a function of its own, so there is
no loop in it to leave. The \ic{;} may be left out before the
\ic{\{\}} closing a block, as after \ic{return}.

\noindent \ic{if let}~\ty{pattern}~\ic{=}~\ty{expr}~\ty{block} is the
pattern form of \ic{if} (Section~\ref{sec:type-unions}): the block runs when
the expression matches the pattern, with the pattern's names bound in it, and
the \ic{else} when it does not. \ic{let} is a whole word, so this is
reached only where the keyword is written; the pattern is whatever a
\ic{match} arm takes --- \ic{some(x)} for an option, \ic{T x},
\ic{T \{f: y\}} for a record type, \ic{\{f: v\}} for equal fields,
\ic{\_} for anything (binding nothing), or a value --- and \ic{some()} binds
nothing. \ty{T} is a record type or one of the language's own names, so
\ic{long n} narrows an option of longs
(Section~\ref{sec:type-unions}); The subject is read once. The
\ic{else} may be left out (a statement, no value), and a pattern that can
fail needs none of its own here: the \ic{else} is the arm that does not
match. The binding is in scope in the block only.

\subsection{Expressions}
\label{sec:expr-grammar}

\begin{align*}
\ty{primary} ::={}& \ty{long} \mid \ty{float} \mid \ty{string}
     \mid \ic{true} \mid \ic{false} \mid \ty{name} \\
  |~& \ic{(}~\ty{expr}~\ic{)} \mid \ic{(}~\ic{)} \mid \ty{block}
       \mid \ic{(}~\ty{expr}~\ic{,}~\ty{expr}~\{,\ty{expr}\}~\ic{)} \\
  |~& \ic{[}~[\ty{expr}~\{,\ty{expr}\}]~\ic{]}
       \mid \ic{[}~\ty{expr}~\ic{;}~\ty{nat}~\ic{]} \\
  |~& \ic{b}~\ty{string} \mid \ty{character}                && \text{(byte string / byte)} \\
  |~& \ic{f}~\ty{string}                && \text{(format string)} \\
  |~& \ic{\{}~[\ty{name}~\ic{:}~\ty{expr}~\{,\ldots\}]~\ic{\}}
       \quad \ic{\{}~[\ty{string}~\ic{:}~\ty{expr}~\{,\ldots\}]~\ic{\}} \\
  |~& \ic{def}~\ic{(}~\ty{params}~\ic{)}~[\ic{->}~\ty{type}]~\ty{block} \\
  |~& \ic{if}~\ic{(}~\ty{expr}~\ic{)}~\ty{block}
       ~[\ic{else}~(\ty{block} \mid \ty{statement})] \\
  |~& \ic{while}~\ic{(}~\ty{expr}~\ic{)}~\ty{block}
       \mid \ic{for}~\ic{(}\,\ty{head}\,\ic{)}~\ty{block} \\
  |~& \ic{foreach}~\ic{(}~\ty{name}~\ic{in}~\ty{expr}~\ic{)}~\ty{block} \\
  |~& \ic{match}~\ty{expr}~\ty{\{}~\ty{arms}~\ic{\}} \\
  |~& (\ic{spawn} \mid \ic{fork})~\ty{block}
       && \text{(threads, processes)} \\
  |~& (\ic{lock} \mid \ic{try\_lock})~\ty{postfix}~\ty{block} \\
  |~& (\ic{join} \mid \ic{post} \mid \ic{wait})~\ty{postfix}
\end{align*}

\noindent The forms a \ic{loop} or \ic{if} takes here are the
statement forms of the previous subsection; they are \emph{expressions}
too, so \ic{let v = if (ok) \{ 1 \} else \{ 2 \};} binds the arm's value
and \ic{let v = while (more) \{ next(); \};} binds a loop's, which is
\ic{void} and so cannot be bound (Section~\ref{sec:void}). \ty{head} is
the comma-separated head of a C-style \ic{for} --- its three optional
parts --- and \ty{arms} the comma-separated \ic{pattern => expr} arms of
a \ic{match}, the last one without its comma
(Section~\ref{sec:type-unions}). \ic{()} is
the void value: nothing is computed, and using it as one is an error
like any other (\ic{cannot bind a void value to 'x'}). \ic{[e; n]} is a
fixed array of \ty{n} elements --- a \ic{[T; N]}, not a \ic{[T]}
(Section~\ref{sec:type-arrays}).
% The postfix row was one line 90pt overfull: an align* row is a box, so it
% breaks only where the source puts a \\ there. Continuation rows carry no
% left-hand side and line up under the first alternative, which is where a
% reader looks for the rest of the rule.

\begin{align*}
\ty{postfix} ::={}& \ty{primary}
   ~\{~\ic{(}~[\ty{args}]~\ic{)} \mid \ic{[}~\ty{expr}~\ic{]}
   \mid \ic{[}~\ty{expr}\,?\ic{:}\,\ty{expr}\,?~\ic{]} \mid \ic{.}~\ty{name} \\
 &\quad \mid \ic{?.}~\ty{name} \\
 &\quad \mid \ic{?.}~\ic{[}~\ty{expr}\,?\ic{:}~\ty{expr}\,?~\ic{]}
   \mid \ic{!} \mid \ic{++} \mid \ic{--}~\} \\
\ty{unary} ::={}& [\ic{!} \mid \ic{-} \mid \ic{\textasciitilde{}} \mid \ic{*} \mid \ic{\&}
   \mid \ic{++} \mid \ic{--}]~\ty{postfix}
\end{align*}

\noindent Postfix \ic{e!} unwraps an option: it is exactly
\ic{unwrap(e)} (Section~\ref{sec:builtin-option}) and, like every
postfix form, binds tighter than the prefix operators --- \ic{!x!} is
\ic{!(x!)}. The two-character token \ic{!=} is always inequality.

\noindent Postfix \ic{e?.name} and \ic{e?.[i]} are \emph{option
propagation} (Section~\ref{sec:type-options}): \ic{e} is read once, and
the rest of the chain runs only when it is there, giving \ic{none} when
it is not. \ic{?.} is one token, so \ic{x?.y} reads the field \ic{y} and
\ic{x ? .y} is not a conditional at all --- maximal munch, as in C,
where \ic{c ?.5 : 1} (a conditional whose arm starts with a fraction) is
a syntax error.
In a record literal a bare name is shorthand for the field of that
name: \ic{\{x, y\}} is \ic{\{x: x, y: y\}} (but \ic{\{ x \}} alone is a
block whose value is \ic{x}).

The forms of threads and processes (Section~\ref{sec:builtin-threads})
are contextual: \ic{spawn} and \ic{fork} start one only before a
\ic{\{}, the other words only before a name, which begins their
\ty{postfix} operand (\ic{join ts[0]}, \ic{lock acct.guard}
\ic{\{ \ldots\ \}}); anywhere else each is an ordinary name. A form is a
call of the builtin of the same name, the block passed as a function of
no parameters: \ic{lock m \{ e \}} is \ic{lock(m,} \ic{def () \{ e \})}.

\paragraph{Tuples.} A parenthesized comma-separated list of expressions is
a \emph{tuple}: \ic{(1, "two")} is a record whose fields are named by
position, so \ic{t.0} and \ic{t.1} read it (Section~\ref{sec:type-records}).
A tuple is an ordinary first-class record value otherwise, and
parenthesising one expression, \ic{(e)}, is still just \ic{e}.

\paragraph{JSON literals.} \ic{json\{}~\ldots~\ic{\}} and
\ic{json[}~\ldots~\ic{]} are source literals for a JSON document. The
sigil is the word \ic{json} immediately followed by \ic{\{} or \ic{[} on
the same line, with no space between. Inside, a bare \ic{\{} is always an
object and a bare \ic{[} always an array (not a Y block or an index), an
object key is a string literal, the scalars are a string, a number (with
an optional leading \ic{-}), \ic{true}, \ic{false} and \ic{null}, and
\ic{json\{} and \ic{json[} may nest. The literal desugars to the
constructors of \ic{std/json.y}: a top-level \ic{json\{} is the bare
\ic{\{str => Val\}} map \ic{json.stringify} takes, an object nested in
another value is wrapped with \ic{json.jobj}, an array is always
\ic{json.jarr}, and the scalars are \ic{json.str}, \ic{json.numtext}
(which keeps the literal's own text), \ic{json.boolean} and \ic{json.nul}
(Section~\ref{sec:builtin-json}).

\subsection*{Operator precedence}

Binary operators are left-associative (\ic{::} is the exception: it is
right-associative, so \ic{1 :: 2 :: a} is \ic{1 :: (2 :: a)}); lower rows
bind tighter:

\begin{center}
\begin{tabular}{cll}
\toprule
level & operators & notes \\
\midrule
0 & \ic{?~:~} & conditional, right-associative, lowest precedence \\
1 & \ic{||} & short-circuit \\
2 & \ic{\&\&} & short-circuit \\
3 & \ic{==} \ic{!=} & structural equality \\
4 & \ic{<} \ic{>} \ic{<=} \ic{>=} \ic{in} & numeric, or lexicographic \ty{str}; \ic{in} is a key/element test \\
5 & \ic{::} & one-element cons (Section~\ref{sec:arrays}) \\
6 & \ic{|} & bitwise or (Section~\ref{sec:bitwise}) \\
7 & \ic{\textasciicircum{}} & bitwise exclusive or \\
8 & \ic{\&} & bitwise and \\
% `<{}<`: the {} keeps T1's << and >> ligatures (guillemets) out.
9 & \ic{<{}<} \ic{>{}>} \ic{>{}>{}>} & shifts \\
10 & \ic{+} \ic{-} & numeric, string/array \ic{+} \\
11 & \ic{*} \ic{/} \ic{\%} & numeric \\
\bottomrule
\end{tabular}
\end{center}

\noindent Unlike C, the bitwise operators bind tighter than the
comparisons, so \ic{x \& 1 == 0} means \ic{(x \& 1) == 0}.

\begin{align*}
\ty{expr} ::={}& \ty{binary} \mid \ty{binary}~\ic{?}~\ty{expr}~\ic{:}~\ty{expr}
\end{align*}

\noindent \ty{binary} is any of rows 1 to 11 above. The conditional
\ic{c ? a : b} is the lowest-precedence form there is: it binds looser than
every operator, so \ic{n < 5 ? "small" : "large"} needs no parentheses, and
it is right-associative, so an arm may be another conditional written without
any (\ic{c ? a : c ? b : d}). It is exactly
\ic{if (c) \{ a \} else \{ b \}}, so \ic{c} is read once and arms that
disagree in type make the whole thing void (Section~\ref{sec:void}). A
\ic{?} immediately followed by \ic{[} is not a conditional at all --- that
spelling belongs to option propagation --- so \ic{x?[0]} is an error and
\ic{x ? [0] : [1]} needs its space.

\subsection*{Assignment forms}

\begin{align*}
\ty{assignment} ::={}& \ty{place}~\ic{=}~\ty{expr} \\
  |~& \ty{place}~\ty{compound-op}~\ty{expr}
     && \ic{+=}~\ic{-=}~\ic{*=}~\ic{/=}~\ic{\%=} \\
  &&& \ic{\&=}~\ic{|=}~\ic{\textasciicircum{}=}~\ic{<{}<=}~\ic{>{}>=}~\ic{>{}>{}>=} \\
  |~& \ty{place}~\ic{++} \mid \ic{++}~\ty{place}
   \mid \ty{place}~\ic{--} \mid \ic{--}~\ty{place}
\end{align*}

\noindent A \ty{place} is a name, an index expression \ic{a[e]} (arrays
and maps), a slice \ic{a[lo:hi]}, or a field expression \ic{o.f}
(records), possibly nested: \ic{grid[0][1]}, \ic{rec.v[2]},
\ic{m["k"]! [i]} (a map read is \ty{V?}, so unwrap it before indexing).
Field access is
symbolic: \ic{r.f} is a record field, and a map reads and writes its
entries with \ic{m["k"]} --- except a map keyed by \ic{str}, where a dot
names the entry too (\ic{m.a} is \ic{m["a"]}, Section~\ref{sec:maps}).
Pointers add \ic{*p = e}.
\ic{++}, \ic{--} and the compound forms store back into the place they
read, so they take a name, an element or a field: a slice, \ic{*p} or
\ic{o!} there is \ic{cannot assign to this expression ('+=')}, with the
operator in parentheses. The bytes of a \ty{str} are read-only, and the
\ic{.length} of an array or a string and the \ic{.ptr} of an array are
read-only to every form.
Section~\ref{sec:exactly-once} defines the exact evaluation of every
form; all of them evaluate the place's subexpressions \textbf{exactly
once}.
